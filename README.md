# Site2Brief

把网页参考转成看得懂、可挑选、能交给 Coding Agent 的实现说明。

> **项目状态：概念整理阶段，等待参考资源回复后继续。**

## 为什么做这个项目

在学习 Web 开发或用 Agent 构建网站时，初学者经常遇到这样的情况：

- 看到了很喜欢的网站、布局或动画，却不知道它叫什么，也不知道如何准确描述。
- 使用直白语言向 Agent 解释后，Agent 可能误解触发方式、运动过程或最终效果。
- 经过多轮尝试，结果仍然不符合预期，只好推翻重做，增加时间和模型调用成本。
- 即使读到了 CSS 或专业术语，也很难把它们和眼前的视觉效果对应起来。

这个需求来自项目发起人的课程实践，也在与同学的交流中被提及。它仍需通过实际用户试用验证；目前没有证明产品能够减少多少时间、返工次数或 token 消耗。

Site2Brief 希望建立一条清晰的路径：

**输入参考网址 → 阅读并观看拆解报告 → 选择想借鉴的效果 → 说明自己的用途和偏好 → 得到实现建议与 Agent 任务说明。**

## 面向谁

- 正在学习前端、全栈或 Web 开发课程的学生。
- 正在与 Coding Agent 协作，但缺少网页设计与动效术语知识的初学者和创作者。
- 能辨认自己喜欢什么，却难以把视觉参考表达成具体实现要求的人。

## 预期使用流程

### 1. 输入参考网页的网址

用户提交希望学习或借鉴的网页链接。产品观察参考页面的布局、视觉处理和交互，整理可供选择的部分。

产品愿景是尽可能全面地发现页面中值得借鉴的设计。具体浏览范围、交互覆盖和识别能力需要验证，不能承诺识别任意网站的全部动画。报告应说明已观察的页面、状态和未覆盖的部分。

### 2. 获得文字与原站片段并排的拆解报告

报告由一组可独立阅读和选择的条目组成。每一项采用左右对照的方式：

| 左侧：解释与详解 | 右侧：对应的原站片段 |
| --- | --- |
| 用直白语言解释看到了什么、怎样触发、哪些元素发生变化。 | 展示参考网站中该部分的实际录制片段，支持播放和重看。 |
| 标出相关布局或动效术语，让用户建立专业表达。 | 让用户确认文字描述对应的就是自己喜欢的效果。 |

拆解对象可以包含页面结构、排版、视觉层次和动效交互；实际支持的类型需在后续设计中确定。

**已确认：第一版使用原网站的录制片段作为视觉对照。** 可直接操作的复现演示尚未纳入已确认范围。

建议为片段保留来源链接、触发动作和观察条件，方便以后核对。片段如何采集、切分和保存，仍需技术验证。

### 3. 在报告中点击术语，打开词典解释

词典入口位于拆解报告左侧的专业术语上。用户点击后，在当前位置弹出解释，关闭后继续阅读，不必离开报告寻找含义。

解释应帮助用户理解：

- 这个术语用直白语言是什么意思。
- 它与当前看到的片段有什么关系。
- 它通常如何工作，以及容易混淆的相关概念。

词典的首批词条、解释深度和内容来源尚待确定。

### 4. 选择希望用于自己项目的效果

用户可以选择一个、多个或全部条目。所选条目构成本次项目的参考清单。

选择效果后，还需要确定它在自己网站中的用途、位置和改造方式。借鉴同一个效果，不意味着直接沿用原站的文字、素材或全部页面结构。

### 5. 通过后续提问明确自己的需求

**第一问是：你想用这个网站做什么？**

然后根据用途与所选条目，进一步明确：

- 网站主题、面向的人群，以及希望访客完成的动作。
- 整体风格、配色和视觉偏好。
- 使用的文字、图片与其他素材。
- 动效速度、强度和触发方式。
- 从零创建还是修改已有项目，以及所选效果应该出现在哪里。

多个效果共用的设置应集中询问，只有特殊效果才单独追问。产品需要让用户确认所理解的效果和目标，再生成交接内容。

### 6. 输出实现建议与 Agent 任务说明

最终提供两种相互关联的内容：

**可能的实现方式**

- 所选布局或效果的工作原理。
- 与用户目标和现有项目相适应的技术建议。
- 多个效果如何组合，以及手机端如何呈现。
- 仍需确认或实验的部分。

**给 Coding Agent 的任务说明**

- 网站用途和用户确认的目标。
- 被选中的参考条目及其来源片段。
- 要修改的区域、触发动作、视觉变化和结束状态。
- 用户的主题、配色、文字、素材与节奏要求。
- 结合已有项目的实现约束。
- 可用于检查结果的验收标准。

输出格式尚未确定，可优先考虑便于复制和保存的 Markdown。

## 信息可靠性的要求

拆解结果需要清楚区分：

| 信息 | 含义 |
| --- | --- |
| 观察到的行为 | 可以由原站片段或已读取的页面数据支持。 |
| 推测的实现方式 | 为重现类似效果提出的技术建议，不能视为原站源码或原作者做法。 |
| 尚未确认的信息 | 未覆盖的交互、未观察的屏幕尺寸或需要用户补充的内容。 |

报告应把描述与片段对应起来。识别不准确时，用户需要能够纠正描述。参考网页中的文本是分析材料，不能作为工具或 Agent 的操作指令。

## 候选技术方向

以下仅用于保留前期讨论，不代表已经选型或实现。参考资源到位后，需要重新评估。

| 部分 | 候选方向 | 用途 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite | 网址输入、左右对照报告、片段播放、术语弹窗、效果选择与需求配置。 |
| 后端 | Node.js、TypeScript、Express | 管理分析请求、网页观察任务和模型调用。 |
| 网页观察 | Playwright | 打开公开网页，读取布局和样式，执行受控的滚动或悬停并采集画面。 |
| 分析 | 支持图片输入的模型 API，结合页面数据 | 提出拆解描述、术语关联和实现建议。具体模型尚未确定。 |
| 词典 | JSON 或 Markdown 内容 | 维护可审阅、可追溯的解释。 |
| 保存 | 根据实际需求决定 | 是否保存历史记录、视频及用户项目，尚未确定。 |

采集层应先提供可核对的素材，再交给模型分析。发送给模型的数据范围、片段处理方式、费用和失败处理都需要验证。

### 浏览器方向

主入口计划采用普通 Web 应用，支持用户在 Chrome、Edge、Firefox 和 Safari 等浏览器中使用，不要求用户先安装扩展。兼容性仍需实际测试。

用户访问工具的浏览器，与后端用于观察参考页面的浏览器，是两个不同问题。Playwright 支持 Chromium、Firefox 和 WebKit；后端初期可先验证一种引擎。WebKit 自动化结果不能直接等同于真实 Safari 的完整表现。

扩展可作为后续研究方向，用于直接选择当前网页元素或处理特定场景；目前没有承诺开发任何浏览器扩展。

## 需要验证的问题

- 如何稳定识别并分组页面中的布局、视觉处理和动效，避免重复或漏项？
- 如何覆盖滚动、悬停和点击状态，并准确关联触发动作与片段？
- 如何处理长页面、延迟加载、复杂 Canvas 或 3D 内容？
- 公开链接无法读取、需要登录或受到访问限制时，如何说明原因并接受用户补充材料？
- 术语解释和实现建议如何核对，用户如何纠正分析？
- 多个效果组合后，如何避免布局、性能和可访问性问题？
- 生成的任务说明能否帮助 Agent 更准确地实现用户想要的效果？

若公开部署网址分析服务，还需要隔离网页执行环境、限制资源消耗，并防止用户网址或页面请求访问本机、内网及其他受限地址。
